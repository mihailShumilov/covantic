## 1. Executive summary

This is a differential audit of everything after PR #4: eight merged commits
(#5–#12) and an uncommitted RPC-resilience migration that replaces every
chain read in the service. 61 files, 5,245 diff lines, reviewed by ten
specialist agents against a frozen scope of 225 files / 53,233 LOC.

**The working tree was dirty by design and moved during the engagement.** The
uncommitted migration is part of the audit target, so the scope is not
reproducible from a commit hash alone. The formal-verification pass also added
six test files and one devDependency (`fast-check`) while the audit ran; those
are listed in §6 and are themselves unreviewed by the other nine agents.

### The three things that matter

**A policyholder can take the vault, profitably and repeatably (ECO-04).** An
SPL `Approve` the agent signs *before* the policy exists produces, at drain
time, exactly the shape the exploit verifier reads as theft: an authority that
is not the agent moved the agent's funds. The holder's own earlier consent is
not merely invisible — `signatures.ts` scores it as *evidence of theft*
(`delegate_transfer`, weight 0.30). Before commit #12 this shape could not open
a claim: the drain does not carry the agent wallet in its account keys, so only
the balance diff saw it, and that raises `balance_drop_unexplained`, which is
deliberately unmapped and goes to a human. **`attributeDrop` removed the
human.** Premium for 100,000 USDC of one-hour coverage is 0.57 USDC; the
working capital returns to the attacker's own wallet in the same transaction
that stages the "loss". The repository ships the sequence as a documented
command (`pnpm agent:trigger --kind drain --sink <pubkey>`), and commit
`2a0c9a7` records it settling end-to-end on devnet.

**The RPC migration's own premise is only half delivered.** It was written
because one provider's quota outage stops the balance checkpoints that bound
every proven payout. Reads now fail over — but (a) the pool does not fail over
on a JSON-RPC error body, which is how a lagging node actually answers
(DEP-01); (b) the checkpoint *writes* deliberately stay on the single primary,
so the original failure mode survives intact (API-15); and (c) all four
proof-posters still read `protocolConfig` off-pool, so a quota outage still
stalls settlement on every proven path (API-08). The health endpoint reports
`ok` throughout all three.

**The prior audit's findings are genuinely fixed, and CEN-01's fix protects
nothing as deployed (CEN-02).** The suspicion that `fix(security)` commits were
stranded on an unmerged branch was **refuted**: PR #4 was squash-merged, and
`origin/feature/actions-detection-improvement` and `2ae9b24` have byte-identical
trees. All seven prior findings re-derived as Resolved, and the deployed devnet
binary is byte-identical to the local artifact with the migration already run.
But `config.admin`, `config.oracle_authority` and the covered mint's authority
are **one plain wallet key**, read live from chain — so the two-step admin
handover added for CEN-01 defends against a typo and against nothing else.

## 2. Findings

### Critical

#### ECO-04 — A holder-granted delegate drain is a one-command, automatically-settled payout

**Economic / Incentive** · Impact Critical × Likelihood Medium · Pending
`workers/exploit-watcher.ts:416-490` · `services/exploit/authorization.ts:275-283` · `services/exploit/signatures.ts:176-189`

`hasUnauthorizedMovement` returns true for any transfer out of the agent's ATA
whose `authority` is not the agent. An `Approve` the agent itself signed
earlier produces exactly that. `isSelf` resolves only the agent and holder
wallets, so a third wallet the holder controls is a `foreignDestination`.
`adjudicateExploit` returns `confirmed` / `unauthorized_loss` at confidence
0.79–0.85, `decideLane` returns `pay`, and `verify_and_payout_exploit` settles
honestly — the money really did leave. Per cycle: −0.57 USDC premium, +100,000
USDC payout, working capital returned to the attacker. `expire_policy` cannot
rescue it (the policy is `ClaimPending`). Bounded only by
`AUTO_PAYOUT_HOURLY_LIMIT_RAW` and the vault balance.

**Fix.** Read the delegate's provenance, not just today's authority: add
`delegateGrantedByAgent` to `MovementRecord`, and treat `true` as
`agent_authorized_movement` (→ review), `null` as `indeterminate`. Secondarily,
require the allowance to predate `policy.start_time`.

### Major

#### API-02 — The read pool's metrics sink is the kit's test-only array; the API OOMs and takes the claim keeper with it
**Volatile Code** · Impact Medium × Likelihood High · `config/rpc-pool.ts:269,330-333`

`InMemoryMetrics` is append-only and documented upstream as "for tests and
local debugging". Nothing prunes it. Measured: **65 bytes per chain read,
permanent** — ~112 MB/day at 20 reads/s, OOM in two to three weeks. `status()`
additionally does an O(n) allocating `filter()` on every unauthenticated
`/api/health/rpc` hit (238 ms per 100 calls at 500k entries). The workers run
in the API process, so the OOM is a settlement outage. **Fix:** implement the
four-method `Metrics` interface locally with counters; `status()` becomes O(1).

#### API-03 — `trustProxy: true` makes `request.ip` attacker-supplied; every rate limit is bypassable
**Data Flow** · Impact Medium × Likelihood High · `index.ts:46-48` · `middleware/rate-limit.ts:29,36-40`

Fastify takes the leftmost `X-Forwarded-For` entry and does not validate it is
an IP (verified: a 200-char junk string becomes `req.ip` verbatim). Every
limiter keys a Redis key on it. Rate limiting is the only control on this API.
Two vectors: unlimited `/api/risk/:addr/refresh` (~35 pool reads each, burns
both providers' quota), and ~8 KB Redis keys filling a 128 MB `noeviction`
instance at ~270 req/s, after which BullMQ `Queue.add` fails and alerts are
dropped. **Pre-existing**, but `TRUST_PROXY` is absent from every compose env
block, so by that file's own rule it is **unsettable in production today**.
**Fix:** `trustProxy: 1`; normalise and hash the limiter key; add
`TRUST_PROXY` to compose.

#### API-05 — `parkedForever` bypasses the tie rule and resets `verifyAttempts`, so a claim can be kept from a human indefinitely
**Design Issue** · Impact High × Likelihood Medium · `workers/claim-keeper.ts:1059-1090`

`if (incoming <= current && !parkedForever) return null` drops the *tie* rule
along with the ordering rule — the comment two lines above still explains why
ties must not swap. The update writes `verifyAttempts: 0`, and
`handleIndeterminate` escalates to `review` only at 5 attempts, so the counter
never accumulates. An attacker alternating exploit(4) and governance(5)
transactions — two per cycle, ~5,000 lamports each — churns the claim between
`pending` and `indeterminate` for the life of the policy. The superseded
`triggerTxSignature` is overwritten with no record. **Fix:** require
`incoming !== current` in every branch; never reset `verifyAttempts`; cap
supersedes per claim.

#### CEN-02 — `config.admin`, `config.oracle_authority` and the covered mint authority are one live wallet key
**Centralization / Privilege** · Impact Critical × Likelihood Low · live devnet config PDA `DtJKLQZjsCWR9vgz6JMxAyhRqkg5GbA81C1H3FtQXjJR`

Read from chain: all three are `4H4G4H5FFApUK4vnqTa9iD6oFHGGavaodKcwULh1SWpv`,
a system-owned wallet, not a multisig. The program separates the roles
carefully; the deployment collapses them. Holder of that key can: pay
themselves up to the vault balance (9,201.74 USDC today); burn any holder's
coverage with a **1-unit** payout (`ZeroPayout` blocks 0, not 1); mint
arbitrary covered token; rotate the oracle; set `paused`. And because they hold
both signatures, `propose_admin` + `accept_admin` completes in two
transactions — **CEN-01's two-step handover assumes admin and oracle are
different parties.** The key is mounted into three containers. **Fix:** split
oracle from admin now (one `update_config`), then move admin to a 2-of-3
multisig.

## 3. Disagreements arbitrated

**The `.all()` owner check.** Three agents said `fetchAllAnchorAccounts` is a
gap because it discards the `owner` the reader already returns; one said it is
not, because `getProgramAccounts(programId, …)` is owner-scoped by definition
of the RPC method. Both are right inside their own threat model, and the
resolution follows from CEN-05: against an **honest** endpoint the filter is
sufficient and the check is redundant; against a **hostile** one the filter is
unenforceable — but so is the `owner` field, which arrives in the same
response. Adding the per-entry check would therefore close nothing that CEN-05
leaves open. Filed as **API-07, Informational (Inconsistency)**: the docstring
at `anchor-reader.ts:32` claims a security property that path does not
provide. Fix the sentence; add the check only as defence against a *buggy*
endpoint, and do not let it read as protection against a lying one.

**Severity of the missing cluster check.** Ranged Major → Minor across three
agents. Settled at **Medium** (GLOBAL-01): impact is coverage denial rather
than theft, and likelihood is raised from Low to Medium by `.env.example` and
the production deploy guide both shipping a literal devnet URL — the line an
operator copies unchanged.

**Severity of `parkedForever`.** Ranged Minor → Major across three agents.
Settled at **Major** (API-05) on the strongest formulation: the
`verifyAttempts: 0` reset is what converts a churn into a permanent denial,
and that detail appeared in only one of the three reports.

**The stranded-fixes hypothesis was refuted, twice, independently.** Both
agents given it verified the trees rather than the commit graph and found
`git merge-base --is-ancestor` returning "no" is the expected signature of a
squash merge. Recorded here because the hypothesis came from the engagement
brief, not from the code.

## 4. Verified clean

Recorded because a coverage claim is only auditable if the negatives are
listed.

- **Evidence determinism across the transport swap.** Verified by independent
  differential reconstruction — one logical transaction rendered as v1
  (`PublicKey` instances, JS numbers) and as kit-on-the-wire (base58 strings,
  bigints) through `toRawTxView` → `canonicalize()`: **identical**. Checked
  against `@solana/rpc-api@6.10.0`'s actual bigint keypath allowlists rather
  than against the reader's claim about them: `plainJson` is load-bearing, and
  `decimals` survives as a `number` because it is on kit's allowlist. Now
  pinned by a committed golden hash and a property test.
- **Pyth guardian verification** cannot be skipped by the lazy receiver
  (commit #5): verification is produced by `addPostPriceUpdates` as on-chain
  Wormhole instructions, not decided by the receiver. No fallback to the
  unverified path.
- **Alert-bus HMAC and webhook auth** unchanged; both branches use
  `timingSafeEqual` behind a length check; every new publisher goes through
  `publishAlert`.
- **The confidence gap holds.** `CONFIDENCE_CEILING` 0.92 < `AUTO_PAY_CONFIDENCE`
  0.95, one definition, imported by all four adjudicators. With the proof flags
  off, `decideLane` returns `review` for every trigger — the unbounded legacy
  `verify_and_payout` is not automatically reachable. **This is what caps most
  RPC-quality findings at Medium.**
- **No provider credential escapes the new code.** `rpcEndpointName` is
  host-only; kit's transport error carries `{headers, message, statusCode}` and
  never the request URL — probed empirically on DNS-failure, 401 and
  connection-refused paths.
- **`solana-resilience-kit@1.3.0` read in full** (2,422 lines): no `process.env`,
  no filesystem access on the imported path, no `eval`/`Function`/`child_process`,
  no dynamic import, no install scripts, no top-level side effects, zero
  dependencies. Published via **npm Trusted Publishing (OIDC)** with a decoded
  **SLSA provenance attestation** naming repo, tag, commit and workflow; the
  lockfile pins `1.3.0` by integrity hash and both Dockerfiles use
  `--frozen-lockfile`. The supply-chain posture is materially stronger than the
  engagement brief assumed.
- **Zero advisories introduced.** All 106 `pnpm audit --prod` findings are
  pre-existing; the two that matter were triaged to unreachable
  (`drizzle-orm` needs `sql.identifier`/`sql.raw`, neither used; `fastify`
  schema bypass needs a route `schema:`, and no route declares one).
- **Lockfile coherent**: 49 packages added, 0 removed, 0 downgraded; no
  dangling symlinks; every entry resolves from npm with a sha512 hash.
- **The three write-reconciliation carve-outs** are correctly on the write
  connection and each carries its comment.
- **`fetchAllAnchorAccounts`' silent drop is not attacker-reachable**: forging a
  program-owned account with a matching discriminator requires the program;
  `allocate`+`assign` yields zeros, excluded by the memcmp filter.

## 5. Limitations

- **The scope is not reproducible from a commit.** The working tree was dirty
  throughout and changed during the engagement (§6).
- **Bankrun suites were not executed** — confirming the prior audit's
  mutation-verification claims needs `anchor build`, which writes into the tree.
  Those claims are structurally consistent but not independently re-run.
- **On-chain authority keys were read but not attested** — the deployed binary
  and account layouts were verified against local artifacts; the upgrade
  authority's custody was not.
- **`cargo-deny` and `trivy` are not installed** — unmaintained crates, licence
  conflicts, and the OS package layer of the built images are unchecked.
  `semgrep` failed to parse `scripts/init-devnet.sh:91`, leaving that file
  unscanned.
- **Detection recall is out of scope.** Nothing here measures how many real
  incidents the screens miss.
- **`attributeDrop` could not be brought under test** without production
  changes or a live Postgres, which is unfortunate given ECO-04 runs through it.

## 8. Upstream: `solana-resilience-kit@1.4.0`

Published 2026-08-31 15:09, after this audit was written. **All three reported
defects are fixed**, verified against the installed package rather than the
changelog:

| Issue | Status in 1.4.0 |
|---|---|
| #15 OTel peer not really optional | **Fixed.** No static import anywhere in `dist/`. `OtelMetrics` resolves a meter from an injected provider, the globally-registered one, or a no-op — better than the lazy-import fix suggested. `@opentelemetry/api` removed from `packages/api` |
| #16 429 never detected | **Fixed.** New `rpc/http-status.ts` exports `httpStatusOf` / `isRateLimited` / `retryAfterMs`, reading the status at top level, under `context`, and under `response`. Verified: a kit `SolanaError` with `context.statusCode = 429` now returns 429 |
| #17 nothing keeps a failing endpoint out | **Fixed, and more thoroughly than proposed.** Health is respected in *both* routing modes; `healthRefreshMs` (default 2 s) gates probe rounds so freshness no longer costs a probe per request; and `HealthMonitor` gained native ejection — `ejectionMs` 30 s, `rateLimitEjectionMs` 5 min, `tryAdmit`, `isEjected`, `ejectedUntil`, injectable clock. It also does **not** record a skipped endpoint as a failed request, which was a separate local correction |

### What that removed from this repository

`config/rpc-pool.ts` lost its hand-rolled circuit breaker entirely — the
`BreakerState` map, `CircuitOpenError`, the cooldown constants, the local
`httpStatusOf`, and the skip-subtraction in `status()`. Ejection is now
configured on the kit's `HealthMonitor` with the same thresholds, and
`status()` reads `ejected` / `ejectedUntil` from `EndpointHealth`.

What remains of the wrapper is one thing the kit still does not do, now filed
as **[#19](https://github.com/mihailShumilov/solana-resilience-kit/issues/19)**:
a node reporting "behind by N slots" answers **HTTP 200 with a JSON-RPC
`error` body**, kit's transport only throws on `!response.ok`, and the pool
only fails over on a throw — so the failure class most likely to be answerable
by a *different* endpoint is recorded as a success. `withJsonRpcErrorHandling`
converts those to throws, maps body-level rate-limit codes onto 429 so the
kit's longer ejection window applies, and deliberately leaves request-shape
codes (`-32600`, `-32602`, …) alone, because every endpoint repeats them and
blaming one would eject a healthy provider for a caller's mistake.

### Still open upstream

**DEP-03 is unchanged.** The peer range is still `@solana/kit ^6.9.0` while kit
is at 8.2.0, so this repository remains on a 6.x line that receives no
security fixes — and that is a decision only a resilience-kit release can
change.
