## 1. Executive summary

Covantic custodies a USDC vault that pays parametric insurance claims for AI
agents. Five on-chain settlement paths exist, four of which bound what the
oracle authority can extract by having the program verify or measure something
for itself.

**The on-chain program is materially stronger than typical for its stage.** The
account-validation discipline is consistent and correct, including the subtle
`associated_token::authority` vs `address = get_associated_token_address`
split, which is a trap this codebase documents and gets right in all five
places. Replay protection on the exploit path uses `init` on an evidence
record rather than `init_if_needed`. No secrets have ever been committed.

Findings concentrate in two places: **capital can exit the vault without the
solvency check that gates new coverage** (ECO-01), and **defence-in-depth is
applied unevenly across sibling code paths** (ANC-01, API-01, ANC-02) — in each
case the correct guard already exists in one path and is missing from another.

## 2. Findings

### ECO-01 — Staker capital can exit below the solvency floor that gates new coverage

| | |
|---|---|
| **Severity** | Major (Impact: High × Likelihood: Medium) |
| **Category** | Economic / Incentive |
| **Status** | Open — design decision required |
| **Location** | `packages/anchor/programs/covantic/src/instructions/unstake.rs:37-113` vs `create_policy.rs:69,72` |

**Description**

`create_policy` refuses to issue new coverage when solvency is too low — it
blocks HIGH-tier policies below `SOLVENCY_CAUTION` and blocks all issuance
below `SOLVENCY_CRITICAL` when coverage is outstanding.

`execute_unstake` applies no equivalent check. It transfers staker principal
out and then calls `vault.recalculate_solvency()` — recording the new ratio
after the fact rather than gating on it. The protocol therefore protects
*future* policyholders from an undercapitalised vault while allowing the
capital backing *existing* policyholders to leave.

**Exploit path**

No exploit is required — this is the rational behaviour of an honest staker.

1. Vault holds staked USDC backing outstanding `total_coverage`.
2. Adverse news (a large pending claim, an exploit in a covered agent).
3. Stakers call `request_unstake`, wait the 48h `UNSTAKE_COOLDOWN`, then
   `execute_unstake`. Nothing on chain blocks it at any solvency level.
4. First movers exit whole. Remaining policyholders hold coverage the vault
   cannot pay — they paid premiums for a promise now unbacked.

This is a bank-run structure: exiting first is individually optimal, which
makes the run self-reinforcing.

**Impact**

Policyholders can hold live, paid-for coverage against a vault whose backing
has legitimately withdrawn. The 48h cooldown is a *detection* window, not a
prevention — `request_unstake` emits an event, so an operator can observe and
pause, but that is a manual off-chain control over an on-chain guarantee.

**Recommendation**

This is a policy choice with real product cost, so it is stated as options
rather than patched:

1. **Solvency floor on exit** — refuse `execute_unstake` if it would push
   `solvency_ratio` below `SOLVENCY_CRITICAL` while `total_coverage > 0`.
   Simple and symmetric with `create_policy`; makes staking illiquid exactly
   when stakers most want out.
2. **Pro-rata exit** — allow withdrawal of the portion that keeps the ratio at
   the floor, queueing the remainder. Fairer, more code.
3. **Coverage-linked lockup** — bind unstake eligibility to the longest active
   policy expiry. Strongest guarantee, worst staker experience.
4. **Explicit acceptance** — document that coverage is backed only by
   best-effort capital, and surface the live solvency ratio to buyers before
   purchase.

Options 1 and 4 are compatible and together are the smallest honest change.

### ANC-01 — Legacy payout path accepted a zero payout, permanently closing a valid claim

| | |
|---|---|
| **Severity** | Medium (Impact: High × Likelihood: Low) |
| **Category** | Logical Issue |
| **Status** | **Resolved** — fix applied, redeploy required |
| **Location** | `packages/anchor/programs/covantic/src/instructions/verify_and_payout.rs:34-45` @ `bf01e5e8` |

**Description**

Four of the five settlement instructions guard `require!(payout_amount > 0,
CovanticError::ZeroPayout)`. `verify_and_payout` — the legacy path — did not.
The comment accompanying the guard in the four siblings states the consequence
exactly: *"A zero payout transfers nothing but still flips the policy to
`ClaimPaid` and releases the coverage — closing a live claim for free."*

**Exploit path**

1. A policy is in `STATE_CLAIM_PENDING` with a valid claim.
2. Holder of the oracle authority calls `verify_and_payout(policy, 0)`.
3. All checks pass: `0 <= coverage_amount`, vault balance sufficient, lock
   elapsed.
4. No tokens transfer. `policy.state` becomes `STATE_CLAIM_PAID`,
   `policy.payout_amount = 0`, `total_coverage` is released, and a `ClaimPaid`
   event is emitted showing a payout of zero.
5. `STATE_CLAIM_PAID` is terminal — the holder cannot re-file. Coverage paid
   for is permanently consumed with no recovery.

**Impact**

Permanent denial of coverage per affected policy, with an on-chain record that
reads as a settled claim. Likelihood is Low because `claim-keeper.ts:797-801`
already rejects `payoutAmount <= 0` before submitting, so the current keeper
cannot reach it — but the program was relying on an off-chain guard for an
on-chain invariant, and the legacy path remains callable by anyone holding the
oracle key.

**Recommendation**

Add the sibling guard. Applied:

```rust
require!(payout_amount > 0, CovanticError::ZeroPayout);
```

**Alleviation**

Fixed in the working tree at `verify_and_payout.rs:45`. `cargo check` clean.
**Not yet live** — requires a program redeploy via the project's runbook.

### API-01 — Unauthenticated demo endpoint gated one variable thinner than the path it feeds

| | |
|---|---|
| **Severity** | Minor (Impact: Medium × Likelihood: Low) |
| **Category** | Inconsistency |
| **Status** | **Resolved** |
| **Location** | `packages/api/src/routes/monitoring.ts:238-241` @ `bf01e5e8` |

**Description**

`POST /api/demo/simulate-exploit` is unauthenticated and unrate-limited. It
inserts a monitoring event and publishes a signed `monitoring:alerts` message —
both inputs the claim-keeper acts on. It was gated solely on
`NODE_ENV === 'production'`.

The keeper's own gate for the same synthetic path, `syntheticAllowed`, requires
three independent conditions and its comment gives the reason directly: *"One
environment variable is too thin a barrier for that: a misconfigured NODE_ENV
on a mainnet deployment would be enough."* That argument applies with more
force at the unauthenticated entry point than at the internal consumer.

**Impact**

On any deployment where `NODE_ENV !== 'production'` — staging, a demo host, a
mainnet deployment whose env was never switched — an anonymous caller can
inject monitoring events and signed alerts naming **any** agent address.
Downstream `syntheticAllowed` still blocks the synthetic *verdict* on mainnet,
so this does not reach a payout by itself; it does reach the claim pipeline,
and there is no rate limit.

**Recommendation**

Share one gate between both ends.

**Alleviation**

Fixed. `syntheticAllowed` and `MAINNET_USDC_MINT` extracted to
`packages/api/src/services/synthetic-gate.ts`; the keeper and the route now
call the same function. Regression test added at
`packages/api/tests/synthetic-gate.test.ts`, mutation-verified: reverting the
gate to `NODE_ENV`-only fails 3 of its 5 assertions.

Rate limiting on this endpoint was **not** added — see Limitations.

### CEN-01 — Admin transfer is single-step with no accept handshake

| | |
|---|---|
| **Severity** | Minor (Impact: Medium × Likelihood: Low) |
| **Category** | Centralization / Privilege |
| **Status** | Open — deliberately not patched |
| **Location** | `packages/anchor/programs/covantic/src/instructions/update_config.rs:28-30` |

**Description**

`update_config` sets `config.admin = new_admin` immediately. There is no
proposed/accepted two-step handoff, so a mistyped or uncontrolled pubkey takes
effect at once and irreversibly.

**Impact**

The admin is the only key that can set `paused` and rotate
`oracle_authority`. Losing it means the protocol can never be paused again and
a compromised oracle key can never be rotated — while the vault stays live.
There is no recovery path in the program.

**Recommendation**

Two-step transfer: `propose_admin` stores `pending_admin`; `accept_admin`
requires that key to sign. Not applied here because it adds a field to
`ProtocolConfig`, changing the account layout and requiring a migration for the
deployed config PDA — a change that needs to be scheduled with the redeploy,
not slipped into an audit patch.

Note what `update_config` gets right: it cannot change `usdc_mint`, and it
bounds `premium_multiplier_bps` to 5000–30000.

### ANC-02 — Unclamped narrowing casts in the staking path

| | |
|---|---|
| **Severity** | Informational |
| **Category** | Volatile Code |
| **Status** | **Resolved** — fix applied, redeploy required |
| **Location** | `stake.rs:32` (`earned as u64`), `stake.rs:112` (`share_bps as u16`) |

**Description**

Two `u128 → u64/u16` narrowing casts had no clamp or fallible conversion.
Neither is currently reachable with a wrong result: `share_bps` is ≤ 10000
while `amount_staked <= total_staked`, and `earned` is bounded by total accrued
premiums. Both depend on invariants maintained in *other* instructions, and the
sibling computation in `InsuranceVault::recalculate_solvency` clamps with
`.min(u16::MAX as u128)` for exactly this reason.

`overflow-checks = true` is set in the release profile, which makes arithmetic
overflow abort rather than wrap — but an `as` cast is a truncation, not an
overflow, and is unaffected by that setting.

**Alleviation**

Fixed. `share_bps` now clamps with `.min(u16::MAX as u128)` matching its
sibling; `earned` uses `u64::try_from(..)` and fails the transaction rather
than paying a truncated reward. `cargo check` clean. Requires redeploy.

## 3. What was verified and found sound

Stated so the reader can tell examined-and-clean from unexamined.

| Property | Result |
|---|---|
| Covered-account derivation across all 5 paths | **Correct.** `associated_token::authority` on exploit/agent-error/checkpoint-balance; `address = get_associated_token_address(..)` on governance/checkpoint-authority — the split the docs require, in all five places |
| Token account constraints on every transfer path | **Correct.** Every `TokenAccount` carries both an owner and a `mint == config.usdc_mint` constraint |
| Double-payout protection | **Correct.** `init` (not `init_if_needed`) on `ExploitEvidenceRecord`; state machine guards `STATE_CLAIM_PENDING → STATE_CLAIM_PAID` |
| Alert channel MAC | **Sound.** Timestamp inside the MAC input, freshness-bounded, `timingSafeEqualHex` comparison |
| Confidence gap | **Holds.** `CONFIDENCE_CEILING` 0.92 < `AUTO_PAY_CONFIDENCE` 0.95 |
| Adjudicator purity | **Holds.** No `Date.now()`, `Math.random()`, `new Date()` or I/O in the four `adjudicate.ts` files (one mention is in a comment) |
| Synthetic path gating | **Sound** (after API-01). Three independent conditions |
| Fail-closed settlement | **Correct.** `planProvenSettlement` returns `unprovable` → review rather than falling back to the legacy path when proof inputs are missing |
| Secrets in git history | **Clean.** No `.env`, key, or keypair file ever committed; no high-entropy assignments in history |
| `update_config` bounds | **Correct.** Cannot alter `usdc_mint`; multiplier bounded 5000–30000 |
| Dependency advisories | **Clean.** `cargo audit` 0, `pnpm audit` 0 |
| Raw account handles / panics in program | **None.** No `UncheckedAccount`/`AccountInfo`, no `unwrap`/`expect`/`panic!` |

## 4. Limitations

This audit does **not** establish the security of the following, which were not
examined:

- **~30k LOC of `packages/api/src`** outside the settlement path — verifiers,
  adjudicator internals, indexer, other workers, DB layer.
- **The entire frontend** (`packages/web/src`), including transaction
  construction and what a user is asked to sign.
- **Docker, deployment scripts, and CI** — no review of image hardening,
  secret handling in layers, or workflow permissions.
- **Economics beyond solvency** — no moral-hazard, adverse-selection, or
  premium-adequacy modelling. ECO-01 came from a structural comparison, not
  from a pricing model.
- **The deployed program.** Source only. No cluster was queried, so the live
  upgrade authority, oracle authority and admin were **not** verified against
  what the source and docs claim. They have differed before in this project.
- **Detection recall.** Open-world problem against an adaptive adversary;
  measured by the labelled corpora, never established by audit.

Tools that could not be run (each a coverage gap): `semgrep`, `gitleaks`,
`cargo-deny`, `osv-scanner`, `hadolint`. Git history was scanned manually as a
partial substitute for `gitleaks`; the others have no substitute here.

No rate limiting was added to `/api/demo/simulate-exploit` — the codebase has a
rate-limit pattern (`riskAssessmentRateLimit`) that should be applied, but
choosing a limit is an operational decision.

Formal verification (engagement phase P4) was **not performed**. The invariants
in `formal-verification` — solvency, conservation, authorization, determinism,
state-machine safety — remain asserted rather than machine-checked. ECO-01 is
precisely the kind of finding a solvency invariant test would have caught
mechanically.
